Human acceptance guide

This is an operator’s guide for the campaign evidence that automation cannot honestly provide: wide visual parity, two real local users with two physical gamepads, and production-host teardown across every physical endpoint.

Use this as a test record, not a dashboard. Checkboxes and notes save in this browser only. Export the JSON with screenshots/log paths after the session. A green automated gate is supporting evidence; it does not replace a required observation below.

Before beginning

Required setup

  1. Use the current campaign build with the relevant debugger modules enabled; do not substitute a mock or direct delegate call.
  2. Have two independently paired physical gamepads, two active local players, a capture tool, and a way to preserve the Editor/session log.
  3. Record build/revision, map or fixture, date/time, monitor resolution/DPI, OS scale, renderer, and controller make/model.
  4. Prepare a clean evidence folder with separate names for wide-reference, two-user, and endpoint-teardown.

Test-record minimum

Required: wide visual parity

Resource Inspector — browser reference versus production

Comparison target: Plugins/CkTests/Resources/ResourceInspector/Workbench.reference.html. This is a wide-reference procedure only. Do not treat a narrow horizontal-scroll capture as responsive/restacking parity.

01 · Lock conditions
Open the reference in a browser and the real production Resource Inspector at the same wide viewport, application scale and zoom.
02 · Match state
Select the same representative item and reproduce the same populated, loading/error, long-label and dialog/popup state.
03 · Capture pair
Capture browser and production without cropping meaningful chrome, including the full window and an optional detail crop.
04 · Judge by regions
Compare hierarchy, spacing, typography, pane boundaries, selected/focused states, overflow, and native-port placement.

Ordered actions

  1. Set browser zoom to 100%; record viewport CSS pixels. Set production application scale and window pixels to the closest controlled equivalent.
  2. Open the reference and production side by side. Ensure both expose the same selected record, search text, pins, and tab/page state.
  3. Capture: baseline populated; long localized label; loading/error; and active dialog or popup if the reference presents one.
  4. Use overlays or side-by-side review at 100% scale. Mark every material mismatch by region, not by an overall impression.

Pass / fail

Pass: wide production preserves the reference’s information hierarchy and intended geometry; text is readable, controls are reachable, selected/focused states are legible, and retained native ports sit in their intended regions.

Fail: clipped/overlapping required content, wrong region order, materially different density/spacing hierarchy, lost state affordance, missing port, or a state that cannot be matched. Record a screenshot pair and exact region.

Do not decide here: browser narrow restacking, accessibility, localization breadth, or the excluded + behavior.

Required: two real users

Two local players · two physical gamepads · ownership and teardown

One keyboard user, one synthetic Slate user, or two pads mapped to the same local player is not evidence. The session must visibly establish Player 1 and Player 2 as separate local players with separately routed physical controllers.

A · Pair
Connect and identify pad A and pad B; create/verify two local players.
B · Navigate
Each player independently moves focus/selection in the same representative production surface.
C · Act
Each uses Confirm and Back; verify only that player’s navigation, action, popup and focus change.
D · Tear down
Hold press/capture or open popup, remove one owner, then prove no stale action dispatch while the other remains usable.

Ordered actions

  1. Record controller IDs and which local player each owns. Start a real two-local-player session.
  2. Put both users on a surface with visible focus/selection and a Confirm action plus Back/dismiss behavior (a dialog, menu, or popup is preferred).
  3. With Pad A, navigate to item A and Confirm; with Pad B, navigate to item B and Confirm. Confirm actions, focus rings and selections remain independent.
  4. Open a popup/dialog with each player in turn. Use Back on the owner’s pad; it must dismiss only that owner’s transient UI and restore the correct owner’s focus.
  5. Begin a press or capture for Player 1 and leave Player 2’s popup open. Close/reopen or deactivate Player 1’s owning surface (or the applicable viewport owner). Preserve a screenshot/video of the transition.
  6. Attempt the held/stale Player 1 action after teardown. It must be inert: no callback, state mutation, popup resurrection, focus theft, or capture leak. Player 2 must still navigate, Confirm and Back normally.
  7. Repeat with Player 2 as the torn-down owner if topology permits; otherwise record why it is not applicable and identify the owner boundary tested.

Required observations

  • Two physical pads and two distinct local players are visible or otherwise recorded.
  • Navigation, Confirm and Back are independently attributable to the correct player.
  • Press/capture release is observed, not inferred from destruction.
  • Popup/dialog teardown is observed; no orphaned popup or focus remains.
  • Held pre-teardown controls/actions are inert afterward.
  • The surviving player remains interactive after the other owner is removed.

Fail: shared focus/selection, cross-player Confirm/Back, lingering capture/popup, any stale dispatch, or survivor interruption. Preserve a short video and exact input/event timeline.

Required: every physical endpoint

28-endpoint production lifecycle checklist

The campaign’s product denominator remains 27 rows. This table is intentionally a 28 physical endpoint teardown matrix: Launcher and Suite are separate Nomad tabs; Input HUD Overlay and Entity Debug Overlay are separate viewport endpoints. The State Machine Debugger entry is the separate CkSmDebugger host, not the ECS StateMachine inspector. HangMonitor is not a denominator row; use it only as extra support coverage.

Run these in order for every applicable endpoint

  1. Open the real production endpoint; establish live content and a retained/native port where applicable.
  2. Exercise close → reopen. Verify no inert tab/viewport widget is retained and the reopened endpoint is live.
  3. Exercise the applicable world/session reset or EndPIE while live.
  4. Exercise module pre-exit/engine-exit teardown in an authorized environment; it must detach without requesting a close from unsafe shutdown state.
  5. With a held callback, focus, capture, popup, or retained port where applicable, release the owner. Verify order: stop work; revoke callbacks/capture/focus/popups; release authored view/ports; detach tab/viewport; clear handles.
  6. Attempt the held action after release. It must be inert. Capture logs and visual evidence.

Endpoint pass rule

Pass: all applicable cells are observed on the production path, no stale dispatch occurs, and evidence identifies the endpoint, run, transition and result.

Fail: a retained inert tab/widget, callback after owner release, capture/focus/popup leak, port still alive after release, unsafe pre-exit operation, or a held action mutating state.

Use N/A only with a concrete reason—for example, an endpoint has no popup or no world binding. “Not observed” is not N/A.
